Design reference

Harbor design tokens

The visual language for Harbor. A restrained palette, purposeful spacing, and room for the work that matters.

Approved visual directionSeptember 13, 2026HTML token reference

Approved visual direction: 2026-09-13. This guide is the canonical visual contract for future Harbor UI work. The standalone HTML prototype demonstrates it; it is not the implemented application and its sample interactions do not establish product capabilities. Architecture and the relevant proposal continue to own product behavior and delivery gates.

01

Design direction and maintenance

01 / ReuseStart with a role.

Use the existing palette, type, and component patterns. A new literal should not become an accidental design decision.

02 / DemonstrateMake the change visible.

Update this HTML guide and the standalone prototype together before application implementation relies on the new pattern.

03 / VerifyCheck the whole interaction.

Review responsive behavior, keyboard use, and pointer states. Preserve product delivery and accessibility verification gates.

Use white, gray, and black, with spacing and subtle shade differences separating regions. Keep the conversation prominent, the sidebar familiar, and everyday actions close to their targets. Avoid decorative color, heavy panels, oversized controls, and extra navigation unrelated to the immediate workflow.

Reuse the tokens and component roles below in future UI work. Some values are existing CSS custom properties; other names describe semantic mappings to literals in the prototype. Do not assume every documented token already exists as a variable or shared application component. Add a semantic token only when an existing role cannot express the need.

When changing this visual direction or adding a new design pattern, update this guide and the standalone prototype in the same change before relying on that design in application implementation. Do not silently override the approved design. Follow the repository's design lifecycle for material contract changes; this guide does not add an approval barrier to already authorized work.

  • The composer begins at one 24px line, grows with content to 160px, then scrolls internally. It shrinks when text is removed. Recalculate on sidebar and viewport resize.
  • Enter sends nonempty text; Shift+Enter inserts a line. Do not submit during IME composition. Disabled send remains visually distinct.
  • Keep project creation beside the Projects heading. Reveal new-session actions on project hover or keyboard focus; expose them persistently on devices without hover.
  • Put Rename chat on each sidebar chat row, revealed on hover or focus-within and always visible without hover. Rename the targeted chat, including an inactive chat, without switching conversations or clearing the draft. Preserve keyboard focus after updating its label. The prototype uses a browser prompt.
  • The desktop sidebar edge is draggable. Use an 8px hit area overlapping the boundary by 4px, with a subtle indicator on hover, focus, and drag. Clamp displayed width to the desktop bounds; retain the preferred width when the viewport temporarily narrows.
  • Expose the edge as a focusable vertical separator controlling the sidebar, with an accessible name and current/minimum/maximum values. Arrow keys adjust by 10px; Home/End select the current bounds. Clean up drag state on pointer release, cancellation, capture loss, window blur, and viewport changes.
  • Mobile sidebar opening makes the main region inert; closing makes the hidden sidebar inert. Support the close button, backdrop, and Escape; restore focus to the opener when appropriate. Switching breakpoints must not strand focus in hidden controls.
  • Use accessible names for icon buttons, aria-expanded for project disclosure, aria-current for the selected chat, and a polite status region for toast feedback. Center desktop toasts in the available main region as sidebar width changes.
  • Keyboard focus uses a 2px outline, generally offset 3px; the separator uses an inset outline. Composer focus changes its border. Do not rely on hover alone to expose actions.
  • Button background transitions use 0.12s; mobile sidebar movement uses 0.18s. Respect prefers-reduced-motion by disabling transitions and smooth scrolling.

Validate changed interactions with keyboard, pointer, touch/no-hover behavior, long titles, multiline input, and desktop/mobile widths. Prototype review is visual and interaction evidence; application accessibility, end-to-end behavior, and backend integration require their own verification.

Conversation actions and resource status · 15 September 2026

Keep the white/gray/black foundation. The resource-status semantic color extension is --resource-active: #27834a, used only for a 6px circular resource-occupation mark. It means confirmed retained runtime or workspace reservation, not connection health or generation. Supply accessible text and a tooltip; a neutral mark must not claim confirmed idle when unknown. Status details describe ownership and release behavior.

Search uses a top sidebar magnifier and an explicitly labelled current-project search dialog (600px maximum, 16px inset) with a prominent 16px input, leading magnifier and close control. Its accessible title and input label are visually hidden. A compact secondary row shows the project with a folder icon and active/archived/all select; archived-project visibility sits beneath. Results are borderless rows with an 18px leading conversation icon, 10px gap and left-aligned labels; use neutral hover/selected fill. Initial focus goes to the input, and results have their own pagination. Search never filters the active sidebar; Escape/backdrop dismiss and restore focus. Expanded project history starts at five rows including the selected open conversation first, then other conversations by durable update time descending (ID descending breaks ties). Selection never changes timestamps; it resets the cursor and reloads the retained depth. Search keeps creation order. Show more adds five; loading disables that control and failure retains rows with Retry. Sidebar status, empty, error, retry and Show more text share the session-title inset: 24px list inset + 12px row padding + 4px dot + 6px gap = 46px from history origin. Search results keep their separate layout. Project rows order label, New chat, ellipsis; project/session and Projects-heading trailing padding is 4px so the plus and ellipsis centers align; the heading plus uses the same 30px slot (36px on touch). Conversation and project ellipsis buttons use centered 16px glyphs from the existing icon system, three filled 1.8px-radius circles, muted neutral contrast and 30px targets (36px on touch). Center glyphs explicitly inside both button and native summary targets with inline-flex alignment; the visible plus-text and ellipsis centers share the trailing column, not just their target boxes. Menu rows have a fixed 18px leading icon column, 10px gap and left-aligned labels. Menus reuse 10px radii, 6px item radii, neutral edges and existing menu shadow. Open with click, Enter or Space; Escape closes and restores focus. Never require hover on touch. Browser tap feedback inherits --selected, preserving neutral gray instead of the native colored tap flash. Settings open from the bottom-right gear; no configuration actions in a toast. The menu shows Codex account, with Set up only when unauthenticated; readiness and onboarding details stay in the account dialog. Omit the work-continues sentence. Dialogs reuse the supporting-surface rules.

Every user message has copy, decorative thumbs-up and decorative thumbs-down beneath and outside its bubble, with 6px separation. The user thumbs are an explicit display-only exception: aria-hidden nonfocusable spans without button semantics, handlers, vote state, requests or persistence. Match the assistant toolbar’s 16px icons, 4px gap and 30px slots (36px on touch). Hide the row only on hover-capable pointers at rest; message hover, keyboard focus and touch reveal it. Failure feedback remains visible. A completed assistant turn has one left-aligned toolbar beneath the final body, ordered copy, like, dislike. Copy uses original Markdown for the full turn, excluding tools and interface labels. Reactions use aria-pressed, are mutually exclusive and toggleable; their state is temporary and has no backend or analytics effects.

Code and literal Markdown blocks have a single neutral header above the scroll area: language at top left (Text when absent), copy at top right. Use 6px 10px header padding, a 1px bottom edge, 11px muted label and the existing icon-button treatment. Keep identical placement on mobile. Copy code without fences or language labels and preserve whitespace. Ordinary paragraphs have no separate copy action. Hover and keyboard focus expose a short tooltip; successful clipboard completion briefly shows a check, then restores the icon. Failures show a brief accessible notice and never a success state. Selected reactions use neutral selected background and ink. No counts or feedback forms.

Conversation Markdown

Assistant messages render CommonMark and GFM: paragraphs, headings, emphasis, lists, disabled task checkboxes, quotations, links, rules, tables, inline code and fenced code. User input and command output stay literal. Accumulated streaming text is parsed again as delimiters arrive; unfinished fences remain code, and an outer four-backtick Markdown fence preserves an inner three-backtick example. Never execute raw HTML or automatically fetch image references; images appear as explicit links. Mermaid fences show a visible “Mermaid source” label and readable code in this release.

Reuse the 15px/1.75 conversation text (14px mobile), 17px/600 headings (16px mobile), 17px paragraph spacing and 12px monospace inline code with #f2f2f2 surface and 4px radius. Code blocks use the soft surface, 1px edge, 8px radius, 12px padding, and 1.6 line height. Language labels use 11px muted text in the block header. Only code syntax may use #8250df (keywords), #0550ae (functions/numbers), #0a3069 (strings), #953800 (attributes/types), and #6e7781 (comments). These content colors never tint shell surfaces, which use equal-channel white/gray values. Bundled highlight.js 11.11.1 supports explicit JavaScript/TypeScript, Python, shell, JSON, YAML, HTML/XML, CSS, SQL, Go, Rust, Java, C/C++ and Markdown aliases, with no detection or network loading. Unknown, unlabelled, Mermaid or blocks larger than 32 KiB stay literal escaped source; highlighting is memoized and copy preserves source bytes. Tables use 1px edges and 8px × 12px cell padding with soft header backgrounds; GFM alignment is represented by CSS classes to respect the application CSP. Tables and code scroll internally and are keyboard focusable. Quotations use a 3px edge and 16px inset. Links are underlined, inherit ink, and use the existing focus outline and muted hover state. The standalone prototype includes desktop/mobile specimens for these patterns.

Personal VPS account settings reuse the account status and explanatory text pattern: show subscription readiness, explain the trusted SSH sign-in step, and omit the API-key form. Unsupported personal-profile tools have no visible entry; capability information remains in project details. Folder browsing stays within approved server roots.

07

Supporting surfaces

The application maps --control-edge to #adadad and --content-width to 760px. Existing component aliases --blue and --danger now resolve to --ink; --line resolves to --edge and --paper to --canvas. These aliases preserve existing component structure without preserving its former colored palette.

P016 refines P014 with one current-project search/filter entry at the top of the sidebar, contextual project details and a bottom-right settings gear. Session ellipsis menus contain existing actions and on-demand status. Do not show unavailable placeholder features. Storage, environment, workspace, connection and retention details live in their corresponding dialogs. Keep actionable failures and approvals visible in the conversation. Consecutive commands in the same operation share one initially closed activity disclosure, including while running. Its 12px muted summary shows command count/running state with 8px vertical padding; expanded details retain literal diagnostics, and expansion survives updates. Approvals/input and actionable errors stay outside it. Command output remains bounded to 32 KiB per command and 256 KiB per conversation.
