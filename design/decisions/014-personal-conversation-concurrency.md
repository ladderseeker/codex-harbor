# D014 — Personal conversation concurrency

- Decision: Accepted, 21 September 2026, under the owner’s P018 implementation and deployment request.
- Execution: [P018](../proposals/archive/018-concurrent-conversations-and-runtime-capacity.md).
- Scope: released personal VPS conversation scheduling. Shared personal-local code remains present, but native macOS lifecycle support is not planned for this release under the owner’s 21 September decision. Shared scheduler regressions retain the managed contract.
- Supersedes: [D005](005-managed-project-workspaces.md) workspace-exclusive conversation ownership only for the two personal profiles. Managed file/Git, terminal, preview and conversation ownership remains exclusive.

## Context and decision

Several personal conversations may work in the same registered directory. The owner coordinates file edits. Each conversation retains an independent native thread, runtime generation and one active turn. No worktree, read-only second conversation or conflict confirmation is required. Local retains its existing read-only ceiling; VPS retains its existing native permission policies.

Migration 019 adds durable session/generation membership with workspace identity, lifecycle, last execution activity, idle deadline and private native process identity. Reserve before launch, persist ownership before any native request, and retain startup/retiring/unknown members in capacity accounting until exact confirmed absence. Never derive capacity from the in-memory map alone. All destructive project/workspace checks account for every member, alongside existing managed writers/readers. An unresolved conversation fences itself; unrelated conversations may use confirmed remaining capacity.

`HARBOR_MAX_ACTIVE_TURNS` defaults to four (range 1–16); `HARBOR_MAX_CONVERSATION_RUNTIMES` defaults to four (range 1–32) and must be at least the active limit. They are administrator admission ceilings, not total process limits or host capacity promises. Active includes startup/dispatch and approval/input waits; runtime includes every non-retired conversation generation. Discovery, terminal and preview budgets remain separate. Lowering limits stops excess admission and converges through completion/eligible retirement without forced cancellation.

A healthy retained runtime can be reused only for its exact generation, permission and credential identity. Scan queued work in stable creation/ID order through the configured bounded queue, skipping blocked entries so a full-capacity new session cannot hide an eligible existing-runtime continuation. Persist bounded queue reasons for session serialization, active/runtime capacity, protected capacity, uncertain retirement, workspace conflict and maintenance; publish only changes. Authority and registered filesystem identity are checked again after waits.

## Idle classification and retirement

Only a successful generation-owned process inspection with no extra descendants is ordinary idle. Exclude only the live guardian and directly launched runtime PID; never allowlist descendants by executable name. The direct pinned native distribution is the verified target. Wrapper descendants conservatively protect a runtime. Startup helpers also protect it while present. Any inspection failure or incomplete identity is unknown. An active operation or pending approval/input is never idle.

Ordinary idle expires after at most 30 minutes and may be reclaimed earlier under capacity pressure, oldest last execution activity first. Polling, viewing and metadata do not refresh activity. Background commands and native attached preview servers are protected while their owned descendants remain; unknown inspection is protected. Neither has an automatic expiry. A browser preview grant alone is not service liveness. No unrelated process is targeted.

Serialize admission/retirement by session and generation. Recheck eligibility, activity and process inspection before retiring. On Linux, each generation uses a unique cgroup-v2 leaf in the supervisor service’s delegated subtree. The supervisor occupies a separate leaf; the paused guardian enters its generation leaf before native startup. Persist host boot identity, path and directory identity before native requests. Descendants inherit membership across process groups, sessions and reparenting. Inspect every member, excluding only the exact live guardian/native identities. Retiring holds capacity until the live-owned, freshly identity-checked cgroup is killed through `cgroup.kill`, `cgroup.events` confirms `populated=0`, and durable release commits. Missing delegation, identity or inspection fails closed, with no group fallback. Failed retirement stays unknown and counted; no replacement slot is invented. Targeted stop, idle-session archive, emergency stop, credential replacement and graceful shutdown may request protected retirement, using the same confirmation. Stale completions cannot release a successor or a sibling.

On restart, conservatively reconcile durable generation-owned identity. Inspect the recorded exact cgroup identity and boot identity without signaling recovered PIDs or cgroups. A populated or ambiguous cgroup stays unknown and counted. Only a verified empty generation cgroup or verified changed host boot can establish absence; a missing or substituted path alone is insufficient. Confirmed absence can release runtime capacity, but cannot label ambiguous operation effects successful or replay old work. Existing personal explicit uncertain-work recovery remains unavailable unless independently implemented and accepted; managed recovery continues its own exact-owner contract. Previously completed native history survives eviction and resumes on explicit new input.

The pinned native probe invalidated the original process-group assumption: standard non-PTY commands create independent sessions and survive native SIGTERM. Darwin lacks a verified unprivileged process-ownership equivalent. The owner selected VPS-only support on 21 September; native macOS concurrency/eviction completion is outside this release and no Linux-container implementation on macOS is selected. No macOS completion or group-based absence claim is permitted. This is a recorded dependency gap, not permission to weaken cleanup. Linux cgroup delegation is restricted to the supervisor; the API remains nondelegated and native sandbox write grants never include cgroup paths. Fixed generated leaves and owned cleanup do not grant arbitrary launcher flags or host administration.

## Interface and delivery

Expose safe runtime state and queue reasons without private process IDs. Multiple sessions in one project may have green resource dots. Keep sidebar ordering by last accepted user query, then the existing fallback/tie-breaker; activity, selection and resource changes never reorder it. Show shared-directory membership and accurate ordinary-idle/protected/unknown status with targeted stop access using existing neutral components.

Promotion drains old exclusive reservations and retains matched database/native/config backup before migration. Older binaries cannot open the upgraded state; rollback requires the compatible checkpoint or forward repair, with explicit consequences for post-backup work. Register new persisted state in backup inventory and invalidate restored process authority. This does not complete the separately unverified managed restore outcome.

Acceptance requires real Harbor same-directory overlap, capacity/fairness/race/restart and denial tests, pinned native process/sandbox contracts, bounded owner-authorized isolated live parallel/reuse checks, supported Linux lifecycle evidence and independent design/provenance review. Missing credentials or infrastructure remain blockers to completion.
