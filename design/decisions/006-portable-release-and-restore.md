# D006 — Portable releases and a fenced host restore

- Decision: Accepted
- Delivery: In progress (design amendment; deployment tooling is not implemented)
- Recorded: 2026-09-07
- Scope: [P009](../proposals/009-portable-deployment-and-restore.md)
- Supersedes: None; concretizes the [architecture release contract](../architecture.md#release-retention-and-rollback-rules)

## Context and alternatives

The deployed profile must package the existing Node 24 TypeScript API and supervisor, PostgreSQL, Caddy, trusted storage service, and Docker runners without weakening their authority boundaries. The current supervisor directly invokes the launcher, Docker and root-only native-storage admission. Separating a root storage service does not make that supervisor unprivileged. Project files and native history have filesystem identity and XFS quota requirements that an ordinary file restore does not recreate.

Building from an editable checkout during installation, copying a live database directory, or restoring old launcher state verbatim would leave artifact identity, cross-store consistency or execution authority ambiguous. The initial implementation instead uses immutable packages, a quiesced backup checkpoint and an explicit fresh-host rebinding step. Online multi-store snapshots and an unprivileged supervisor behind a new launcher RPC are excluded from this decision; they require separately recorded designs.

## Installed layout and services

Use the following fixed layout, with an installation instance ID restricted to the existing safe identifier grammar. Administrator-selected XFS mount locations remain configuration values and must pass the existing trusted-path checks.

| Location | Authority and contents |
| --- | --- |
| `/opt/codex-harbor/releases/<artifact-digest>/` | Root-owned immutable package: built web assets, TypeScript service sources and pinned execution dependencies, Node 24 executable, migration files, Compose/service definitions, policy artifacts and administrator tooling |
| `/opt/codex-harbor/current` | Root-controlled selection of an installed release; running services use the resolved immutable path until deliberately restarted |
| `/etc/codex-harbor/<instance>/` | Validated configuration and protected secret files, readable only by their trusted consuming services |
| `/var/lib/codex-harbor/<instance>/` | Control database storage, launcher authority, workspace receipts, release/backup records and bounded private staging; outside the project filesystem |
| `/run/codex-harbor/<instance>/` | Recreated private sockets and transient service state; excluded from backups |
| Configured XFS roots and pool | Quota-backed complete project units, with trusted parents and fixed runner ownership under D003 |

The package manifest records source and artifact digests, CPU architecture, exact Node/pnpm/dependency versions, database schema digests, configuration and backup schema versions, PostgreSQL/Caddy/runner/gateway/Git-helper image digests, Codex/native-history compatibility, and seccomp digest. Node remains on the tested 24 line; the exact binary version and checksum are fixed in each release. No dependency installation, source build, floating image resolution or automatic tool self-update occurs during promotion. Authenticate the expected package digest through the trusted distribution/administrator channel before unpacking into a new root-owned release directory; a checksum shipped beside an untrusted download is insufficient provenance.

Systemd supervises separate API, supervisor and storage services, plus the instance's fixed Compose dependencies. PostgreSQL and Caddy use pinned containers. The API uses a dedicated unprivileged account, a loopback listener and the narrow private credential/storage sockets. The supervisor remains a trusted root service in this initial profile, as does the storage service; only these trusted services and administrator tooling receive the required Docker/storage authority. Runners, the API and Caddy never receive Docker or administrator sockets. Do not run repository hooks or project-supplied commands in these host services.

Socket access must work for that real UID separation: use root-controlled, non-client-writable parents with narrowly granted traversal and mode-0600 endpoints assigned to the configured API client identity. The storage service already has explicit trusted-client configuration; the credential service's current same-UID private-parent assumptions require a bounded deployment integration change. Preserve root-controlled ancestry, explicit client UID/GID denial for runner/proxy identities, fixed request schemas and server-side current-authority validation. Do not solve IPC access by making sockets world-accessible or running the public API as root. Verify the packaged services under their actual configured identities.

Only production Caddy HTTPS and explicitly configured SSH administration are public. PostgreSQL and API bindings remain loopback/private. Production Caddy uses the configured canonical origin and verified TLS, with persistent certificate state; the existing loopback `tls internal` test configuration is not a public deployment template. Service readiness distinguishes database/API health, launcher admission and account capability readiness. Missing model credentials yields an explicit unavailable account state, not a fixture fallback or a claim that conversation acceptance passed.

Before execution admission, measure local Docker context, supported kernel/architecture, exact images, seccomp, isolated runner/gateway networks, fixed approved-endpoint connectivity, and D003 accounting/enforcement, unique project IDs, inheritance, ownership and byte/inode headroom. Control state must reside on a different filesystem from project quotas. Missing prerequisites fail closed. Installer preflight never reformats an existing filesystem or changes the ownership of an existing personal repository; administrator provisioning of suitable storage is explicit.

Preflight also compares allocated quota slots with registered database projects and the backup registry. Initial P001 project allocation still performs a filesystem effect inside a database transaction; [source inspection identifies possible COMMIT-loss orphan slots](../../issues/2026-09-07-205511-unregistered-project-allocation.md), while P003 receipts cover derived workspaces only. Detect and report unmatched allocated slots, quarantine them from allocation/backup-completion assumptions, and provide explicit administrator reconciliation after exact identity, quota and content validation. Never delete or automatically adopt unknown data. An existing valid directory may be registered through the supported explicit existing-project path; record the decision and recheck the registry before backup. Keep the trusted receipt protocol extensible for future bounded initial-allocation reconciliation without claiming it already exists.

## Backup checkpoint and encryption

Pin [Restic 0.19.1](https://github.com/restic/restic/releases/tag/v0.19.1), including the architecture-specific binary checksum, in the initial package. Use its encrypted repository format with a configured off-host destination; the first portable transport is a restricted SSH/SFTP destination with a pinned host key. Disposable A-to-B tests may use their owned SSH destination. Backup access credentials and the repository recovery password stay in protected files and out of command arguments/logs. Keep a recovery copy outside the installation and outside the repository it unlocks. This is separate from the model-credential encryption key. [Restic encryption](https://restic.readthedocs.io/en/stable/070_encryption.html)

One administrator deployment lock serializes backup, restore, promotion and schema work. The checkpoint sequence is:

1. Persist maintenance/admission-disabled state. Reject new application mutations, including credential changes, uploads and metadata operations; stop admitting new turns. Allow only the bounded controls required to finish draining.
2. Drain active work or explicitly interrupt it with visible consequences. Confirm exact runner, helper, probe and surviving background-process retirement. Settle accepted workspace storage commands and recovery effects before publishing a checkpoint. Unresolved external metadata effects make backup unavailable until trusted reconciliation completes; do not silently cancel or omit them.
3. Stop application, supervisor and storage writers. Prevent automatic restart until the checkpoint ends. Retain uncertain operations and their provenance, expired approvals, queued input and writer reservations in the checkpoint; backup is not recovery acknowledgement. External SSH writes during this window violate the checkpoint and must be excluded operationally.
4. Export the instance database using pinned PostgreSQL `pg_dump` custom format into bounded mode-0600 control staging, then back up that export, registered project units and protected configuration in one Restic snapshot. Recreate deployment roles separately rather than restoring unrelated cluster roles. A database-consistent dump alone does not synchronize filesystem state. [PostgreSQL dump semantics](https://www.postgresql.org/docs/17/app-pgdump.html)
5. Require exit 0, exact snapshot identity and complete registry coverage. Run `restic check --read-data` for the backup used in release/restore acceptance. Write a protected completion record containing snapshot ID, manifest digest, checkpoint time and verification outcome only after success. Restart the original installation only according to its recorded maintenance/admission state; failure never silently enables work.

The encrypted snapshot contains protected secrets in a separately enumerated registry class, including the model encryption key needed to recover the ciphertext. Do not create a plaintext credential tar/archive or export the model key into the SQL dump. Private staging is bounded, never served, and cleaned only by its owned operation ID. Exclude redundant native `auth.json` credential copies; restored runtimes authenticate from the protected credential broker. A missing original model encryption key requires explicit re-onboarding rather than fabricated successful recovery.

Treat an unreadable source, missing registry unit, exhausted staging/repository capacity or nonzero Restic exit as failed backup. Exit 3 may create an incomplete snapshot, and default `check` does not read all pack data; neither establishes a valid Harbor recovery point. Retain previous verified snapshots and separate retention/prune operations from backup failure cleanup. Encryption does not prevent an attacker holding repository write credentials from deleting backups. [Backup failure semantics](https://restic.readthedocs.io/en/stable/040_backup.html#exit-status-codes), [full data checking](https://restic.readthedocs.io/en/stable/045_working_with_repos.html)

## Versioned backup registry

The installed release owns a fixed, versioned registry of module IDs, schema versions, required database objects, approved relative filesystem units, bounded size/count checks and trusted restore validators. A backup cannot supply executable restore hooks, shell commands or administrative absolute destinations. Fail on an unknown required module or missing expected unit. Unimplemented modules have no placeholder entry; each later data owner extends this registry and its restore acceptance.

| Delivered module | Consistent state and restore obligation |
| --- | --- |
| P001/P002 | Database history, intents, audits, grants and runtime credential ciphertext; protected encryption/configuration secrets; native homes; authority revocation on restore |
| P003 | Workspace and storage-operation rows, trusted receipts, and each complete project quota unit: Local, derived checkouts, common Git metadata and native homes; new filesystem binding with stable logical UUIDs |
| P007 | Recovery attempts, acknowledgement/provenance and replay/history records, alongside the matching native history; no automatic continuation or invented terminal result |
| P005 | PostgreSQL attachment blobs/drafts and materialized per-session attachment directories within project quota units; digest/reference and filesystem validation before admission |

Include registry version, source instance/owner pin, release/schema compatibility, recovery point, root/project/workspace/session IDs, quotas and content manifests. Caddy state and protected configuration are separate from project content. Live sockets, PID files and transient locks are excluded. Old launcher ledgers and storage receipts are retained as protected historical evidence, not activated unchanged on a different host.

## Fresh-host restore and authority

Restore into a new disabled installation namespace and new database, never into a healthy instance's active paths. Verify encrypted snapshot integrity and manifest compatibility before publication. Provision fresh quota roots and project IDs under destination D003 policy; quota limits must accommodate the recorded data and current reserves without an unapproved increase. Do not assume file-copy tools restore project attributes or safe ownership.

Restore project content only into fresh staging whose namespace cannot reach host administration. Reject special files and unexpected mounts; preserve ordinary content and symlinks without following them, remove privilege-bearing modes/capability metadata, and apply the fixed trusted-parent/runner ownership policy. Validate the destination again before publishing. Restic preserves symlinks, can restore device files, and does not preserve all inode metadata, so raw extraction is not a trusted provisioning operation. [Restic metadata behavior](https://restic.readthedocs.io/en/stable/040_backup.html#backing-up-special-items-and-metadata)

Use a new instance ID and retain the backed-up owner issuer/subject pin by default. A different owner is a separately recorded administrator rebinding action and never inherits active browser/PAT grants. Revoke all restored browser sessions and PATs, rotate host/database/IPC secrets, expire approvals, and invalidate discovered account/model caches. Convert queued execution/control work into explicit non-dispatchable restored records under a bounded migration; do not replay it. Preserve original uncertainty and acknowledgement history. Recovery readiness tied to A's generation becomes invalid on B and requires a fresh P007 fence/inspection before deliberate continuation.

Recover the model credential using its old key and authenticated instance/owner context in trusted memory, then re-encrypt it with a fresh destination key and B's authenticated context. Never change the instance ID and then attempt to decrypt old ciphertext as if it already belonged to B. Remove native credential copies before any runtime starts. The repository password and source decryption material are supplied out of band, not recovered from unauthenticated application routes.

Preserve logical root/project/workspace/session UUIDs and fixed container paths, including managed Git aliases. The trusted restore transaction derives and records new canonical/device/inode bindings from validated destination files. Old pending/failed storage command payloads and their receipts may contain A's identities and hashes: preserve them for history, revoke their retry authority in the restored namespace, and require fresh destination commands for later work. Do not rewrite a command while pretending its old receipt still authenticates it. A normal completed checkpoint has no unresolved external metadata commands; restore rejects one that does rather than guessing how to replay it.

Create fresh launcher authority with a destination restore epoch that fences prior generations. Do not import active lock directories, container identifiers or network grants, contact A's Docker daemon, or clear A's resources. Reconcile restored writer reservations only through explicit confirmed-absence/P007 recovery semantics; preserving uncertain work does not authorize releasing it silently. Until all required validators pass, API remains in maintenance mode and automatic supervisor discovery, probes and execution remain disabled. After filesystem/identity admission passes, the trusted validator may launch a bounded confined read-only native compatibility probe under fresh destination authority; it cannot submit a turn or answer an approval, and its retirement must be confirmed. Activation is a distinct recorded operation after destination checks; failed activation leaves B disabled and A untouched.

## Promotion, rollback and SSH recovery

The planned trusted `harborctl` entry point provides fixed install, preflight, status, drain, backup, restore, promote, rollback and recovery operations. These are design contracts, not currently available commands. Operation inputs are installed artifact/instance/backup IDs and validated configuration, never project-supplied flags or restore scripts. Persist bounded operation state before external effects so process loss can reconcile only owned staging/services.

Promotion references an immutable tested artifact and compatibility manifest. One deployment/migration owner holds the lock; startup must not let both application services migrate independently during a switch. Use the architecture's drain and compatible HTTP-only switch rules. Retain the old release, but allow rollback only while schema, configuration and native history are readable by that release. Refuse incompatible downgrade before changing traffic; deliberate restore or forward repair records possible lost writes and is not an automatic fallback.

An SSH runbook and installed administrator tooling remain usable with Caddy, API and supervisor unavailable. They inspect readiness, restore a compatible release, verify a backup, and retire exact recorded owned runtimes/helpers before recovering stale locks. Never broadly remove containers or delete all lock files. Existing user authorization governs promotion and recovery; this decision creates no extra permission gate.

## Evidence and remaining gates

[P009-01–07](../proposals/009-portable-deployment-and-restore.md#independent-acceptance) own the complete fresh-install, reboot, A-to-B restore, failure, rollback and SSH outcomes. The first B is a disposable Ubuntu 24.04 arm64 VM with Docker 29.1.3, Node 24/pnpm prerequisites and a dedicated XFS filesystem; those installed prerequisites are not evidence that Harbor deployment is verified. Record exact image/artifact versions, kernel/filesystem/quota results, source and backup digests, commands, exit codes and resource use for both hosts.

Test restored logical/content identity with different destination device/inode identities, revoked old cookies/PATs, model credential re-encryption, retained uncertainty, fresh recovery, workspace Git/common integrity, attachment references, denied old receipt retries and zero contact with A's runtimes. Inject partial backup, missing secret/module, corrupt data, disk pressure and restore-process loss; neither healthy A nor an existing healthy B installation may be replaced. Exercise incompatible downgrade and out-of-band recovery with Harbor unavailable. Approved-endpoint connectivity measurements do not waive TLS/routing denials.

Real pinned-Codex/account and supported Linux checks remain mandatory. [Dedicated live credentials are unavailable](../../issues/2026-09-07-171225-live-runtime-credentials.md); [gateway availability remains open](../../issues/2026-09-07-185228-linux-gateway-availability.md). This accepted design does not establish installation commands, an executed restore, deployment readiness or P009 completion.
