# D008 — Confined workers for Harbor self-development

- Decision: Accepted
- Delivery: In progress
- Scheduling update: [D009](009-common-use-release.md) defers P010 implementation on 2026-09-13. This worker/isolation contract remains accepted and its unfinished gates remain required when work resumes.
- Recorded: 2026-09-08
- Scope: [P010](../proposals/010-self-development.md), refining the [architecture's trusted build/test broker](../architecture.md#developing-harbor-through-harbor)
- Supersedes: None. This selects a concrete worker boundary; it does not grant candidate code the stable supervisor's authority.

## Context and choice

P009's initial supervisor and storage service require root and Docker authority. Running a candidate copy of those services as host processes would execute editable project code with stable-host privileges. A different Compose name or Docker label does not confine a candidate with the host daemon socket. Reimplementing the complete candidate launcher as a filtered Docker API would create a large new authority surface.

The initial broker instead creates a dedicated, bounded **worker container containing an emulated disposable Linux guest**. The guest runs its own native Docker daemon and actual candidate Harbor services. It receives no host filesystem share, daemon, administrator credential or device. QEMU runs as an unprivileged process inside the outer worker container. Assume malicious guest code can compromise that whole outer worker: the outer container's fixed namespaces, mounts, capabilities, seccomp, network and cgroup limits are the host security boundary. Guest root can administer only that job's disposable guest resources.

This distinction is deliberate. QEMU documents that TCG emulation is outside its supported guest-security guarantee; Harbor does not rely on TCG as that guarantee. Hardware virtualization is not silently required on a VPS or on the local Apple M2 development machine. No KVM, privileged container, host namespace, nested Docker daemon in the coding runner, or relaxed host policy is an automatic fallback. The outer worker must independently pass actual Linux confinement checks. [QEMU security requirements and least privilege](https://www.qemu.org/docs/master/system/security.html)

## Immutable worker and guest inputs

The administrator installs a trusted worker image and sealed guest base, recording OCI/binary/firmware/base-image digests, architecture and exact tool versions in the release manifest. Use fixed headless QEMU devices and TCG settings, no passthrough, display server, shared directory, user-supplied disk/backing chain, monitor command or kernel parameter. The administrator prepares the guest from a verified distribution image with pinned Node/pnpm/Codex, PostgreSQL/Caddy/runner/helper images and a dependency cache for the approved Harbor lockfile. This preparation runs before any candidate source is present. Its package downloads and cache changes are separate trusted administrative operations.

Runtime workers are offline. Dependency installation uses the supplied cache and frozen lockfile; a missing dependency/cache identity is an explicit unavailable result, never permission for arbitrary downloads. A candidate may modify its own dependency scripts and Dockerfile, but they execute only in its guest. Neither they nor its package manager can redefine the outer worker image, mounts or limits. Unsupported platform/dependency/image changes require a new reviewed administrator bundle and corresponding acceptance; ordinary application changes use the same installed bundle.

Each worker receives one immutable source snapshot, a read-only sealed guest base, a fresh writable guest disk and run-owned transfer/output space. A trusted process creates the writable disk from a fixed format; do not let QEMU inspect a project-supplied image on the host. Input/source/artifact archives are treated as untrusted data with explicit sizes/manifests, no-follow extraction and no executable host hooks. The broker never mounts a candidate filesystem into the host to inspect its files. Transfer uses a fixed guest control channel and bounded byte protocol.

The worker container uses a dedicated nonroot UID, read-only root filesystem, dropped capabilities, no-new-privileges, a fixed seccomp policy, private PID/IPC/network namespaces, and only its exact job mounts. It receives no `/dev/kvm`, host socket, host `/proc`, host administrator path or other job directory. A dedicated quota-backed worker filesystem is separate from stable control/project filesystems. Initial bounds are one active worker, two vCPUs, a 4 GiB guest, 5 GiB outer memory including QEMU overhead, 256 outer PIDs, a 16 GiB writable disk and a two-hour total job lifetime. The configured host must reserve at least two CPU equivalents, 2 GiB memory and control-disk recovery headroom for stable Harbor, in addition to the worker allowance; otherwise admission refuses. Apply actual cgroup and hard disk limits rather than estimating guest use.

QEMU user networking uses `restrict=on`, IPv6 disabled, and only fixed loopback guest-control/candidate forwarding inside the outer container. The outer container has no routed network. The broker accesses those fixed channels through an exact-container stdio helper; no host port is published and no arbitrary TCP/URL proxy is exposed. No guest forwarding to host commands, TFTP/SMB share or mutable network rule is accepted. QEMU describes restricted user networking as blocking guest-to-host and outbound routing except explicitly configured forwarding; actual outer-container denials remain independently required. [QEMU user-network controls](https://www.qemu.org/docs/master/system/qemu-manpage.html)

## Stable authorization and source snapshots

The browser explicitly enables development commands for a registered Harbor source workspace and selected conversation. Current owner/instance/project authority and workspace-write ceiling are required. The stable service issues a short-lived, random capability bound to that exact instance, project, workspace, conversation generation, allowed command profiles, expiry and job limit. Store only its hash in trusted state. A read-only capability file in the assigned coding runner and a fixed narrow build gateway permit submit/status/log/artifact-reference operations for that assignment only. No ordinary owner cookie/PAT, deployment permission, secret administration or generic launcher call enters the runner. Revocation/expiry stops future requests, without pretending to undo an already accepted build.

The build gateway is a separate fixed service on the assigned runner's existing private network, with a narrow authenticated broker socket. It forwards only the fixed job protocol and supplies no generic host route or model-policy exception. The gateway has no Docker socket or source mounts. The broker checks current capability, generation, actor/owner pin, profile and exact workspace identity after lock waits and before acceptance. It commits job identity, request hash, source-capture intent and resource ownership before external effects. Duplicate requests reconcile the same job; changed payloads under an existing key fail.

The source snapshot contains bounded actual Harbor source and the committed lockfile, excluding fixed administrative/state paths such as `.git`, credentials, dependency caches, build outputs and test runs. Include ordinary new source files; do not silently assume a clean Git commit. The trusted copy helper treats all bytes as untrusted and applies P003 path/identity checks. Record a complete file manifest and SHA-256 digest of the copied input. After copying, recheck source identities and the whole bounded file manifest; a changed source returns conflict and requires a new capture.

Capturing from the requesting conversation may occur while it owns the writer reservation. This is an explicitly optimistic capture bound to that exact writer generation, not a new writer or an atomic filesystem snapshot. Its before/after checks detect observed changes; the immutable copied bytes and their manifest are the build authority. A hostile writer choosing those bytes gains no host authority. For a different writer/generation or conflicting metadata operation, use ordinary P003 admission and refuse/wait visibly. Do not release, replace or acknowledge the source writer as a side effect of requesting a build.

The fixed runner command wrapper routes supported `pnpm build`, `pnpm check`, `pnpm test`, `pnpm test:e2e` and candidate `pnpm dev` requests through that capability. It accepts no arbitrary shell command, working root or resource flag. Project scripts can change how a command behaves inside the guest but cannot change broker policy. Developer-shell entry points keep their documented local behavior; the self-development harness uses the same broker profiles and provisioning contract. No manual host-privilege bypass may be required for the supported workflow.

## Build, independent verification and candidate access

Build in one disposable guest from the recorded source snapshot. Candidate guest database roles, OIDC fixture, browser/session secrets, native homes, project roots, ports and launcher state are fresh. They are never copied from the stable instance. The guest may contain its own root services and daemon because all their authority stays within the confined worker. Candidate output and self-reported tests are untrusted results, not sufficient release evidence.

After a build, collect the exact bounded artifact bytes and digest, retire the build worker, and install those same bytes in a fresh verification worker. The trusted verifier and report authority run outside both the candidate guest and the entire outer worker, with no writable report/signing-key path available to either. A separate confined browser process receives only disposable candidate credentials and the fixed candidate destination, without stable administrator mounts; it does not share the stable browser's credential state. The trusted controller records required API/browser observations through a bounded protocol and persists the report itself. Candidate/worker stdout and self-reported tests remain untrusted data and cannot mint a passing report or change the required external checks. A changed artifact invalidates its report; preparation never rebuilds different bytes after testing. Verification proves the recorded scenarios, not arbitrary candidate-code correctness or host-wide security.

The successful candidate is inspectable only through a unique private HTTPS origin distinct from stable Harbor and every other candidate. Reuse the browser-grant, one-use bootstrap, host-only cookie, current-authority and bounded stream principles in D007 without depending on P011's project process launcher. Proxy only that job's fixed guest candidate port via the broker; never accept a client destination. Strip stable/broker credentials before forwarding. Candidate HTML/scripts are untrusted and may not run under the stable origin, receive stable cookies, navigate an opener or reach a raw broker/admin route. A candidate has fresh fixture identity/configuration and its own Harbor login state in addition to the outer viewing grant.

Normal candidate tests use deterministic Codex/OIDC at their external boundaries and offline dependencies. P010's dedicated live gate drives real coding in the stable conversation through the same broker; it does not require putting the stable model credential into candidate code. Required release runtime/Linux checks retain their own trusted lanes and artifact identity. Candidate fixture success does not satisfy P009's backup/restore or missing live-account gates.

## Retirement, retention and release boundary

The broker owns durable phases `accepted`, `capturing`, `building`, `verifying`, `ready`, `failed`, `stopping`, `stopped` and `uncertain`, plus immutable source/artifact/report identities. Never restart or replay an ambiguous candidate job automatically after broker failure. Close viewer routes first, retire the exact immutable worker container and children, then release capacity and remove only its registered writable disk/transfer paths. Unknown retirement keeps capacity reserved and visibly blocks another worker. Expired capabilities cannot mutate a successor or recover broad authority. External SSH administration can inspect/stop the exact job while Harbor is down.

Bound logs/results and job records, reserve independent cancellation/recovery records, and keep immutable release evidence separately from disposable guest disks and credentials. P010 owns the exact API limits. P009 backs up durable manifests/reports and recorded artifact references; transient worker secrets/disks are excluded. Restored jobs are historical and non-dispatchable; capabilities/viewer grants are revoked and no source-host worker is contacted.

Preparing a release verifies the artifact digest, trusted report, required gates and compatibility, then returns a reviewable P009 release reference. Candidate code and its capability cannot promote, back up or administer the stable installation. Promotion remains P009's independently authorized operation, including checkpoint, drain or explicit interruption of the development conversation, migration and rollback compatibility. The owner has authorized this task's implementation, but the separately recorded automatic-review backup-transfer rejection remains a real gate; this worker path cannot bypass it.

## Verification status

One independent design review and focused correction check closed on 2026-09-08. The correction places verification/report authority outside the entire potentially compromised worker and requires a forged-report denial. No actionable design finding remained. Implementation is in progress; complete feature and isolation acceptance remain pending. A separate task-owned Linux test host has bootstrapped with no host mounts or agent forwarding and bounded resources; that preparation is not worker confinement evidence. P010's acceptance must exercise real source edits, broker/guest/candidate services, fixed external checks, malicious worker inputs, host and cross-job denials, actual resource exhaustion, exact cleanup, stable responsiveness, and tested-artifact promotion rules. A compromised-worker canary attempts to change the trusted verifier/report store and submit a forged success; neither may qualify the artifact. Local documentation checks cannot establish any of those results.
