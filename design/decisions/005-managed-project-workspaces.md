# D005 — Managed parallel project workspaces

- Decision: Accepted
- Recorded: 2026-09-07
- Scope: [P003](../proposals/003-parallel-project-workspaces.md), extending [D002](002-registered-mount-authority.md) and [D003](003-quota-backed-project-storage.md)
- Delivery: In progress; acceptance evidence is owned by P003

## Context

A repository-controlled `.git` path is not a safe host bind-mount authority. Git worktrees share metadata and Git configuration can cause executable hooks, filters, helpers, and external path accesses. Parallel checkouts need independent writer admission without weakening the project runner or persistent quota boundary.

## Decision

Each managed project retains its existing Local `workspace` and gains administrator-controlled sibling directories for derived `workspaces/<workspace-id>/checkout`, `git-common`, and native session homes. All descendants inherit that project's existing unique XFS project ID and hard byte/inode limits. The service persists checkout and common metadata device/inode identity. It mounts only the selected checkout at `/workspace`, that project's common Git metadata at `/git-common` when needed, and the session's existing stable native home. Project and workspace parent directories remain trusted; repository-controlled children never become bind authority. Other projects and other checkouts are absent from the runner. A selected worktree also has a fixed identity-derived alias `/harbor/workspaces/<workspace-id>` for Git administrative back-references; both mounts refer to the same validated checkout inode. Common entries use the unique workspace ID, `.git` points to `/git-common/worktrees/<workspace-id>`, and `commondir` resolves inside that mount. Managed entries are locked against automatic pruning. Registry IDs and validated inodes, never Git-supplied back-references, authorize removal; generic prune/repair is not a service operation. The common mount is read-only for a read-only runner and writable only under workspace-write, whose sandbox roots include the selected checkout aliases and common metadata.

The Local checkout remains unchanged when creating a derived workspace. The first Git Worktree request imports committed objects into a new managed bare common repository using a fixed confined Git helper; it does not move or bind the Local checkout's `.git`. Derived Git worktrees share this managed common repository. Subsequent requests resolve an explicit commit from that managed repository, or explicitly refresh committed objects from Local under an exclusive project metadata reservation. A dirty Local checkout is reported and its uncommitted changes are excluded from Git worktrees. Creation displays this policy and the immutable base object ID. Worktree metadata sharing is intentional within one project and is not a security boundary. [Git worktree metadata](https://git-scm.com/docs/git-worktree)

Git runs only in a fixed nonroot Linux helper image, with the runner's privilege/resource/seccomp bounds and no network. The source checkout is read-only and only owned staging/common paths are writable. The helper accepts opaque registered IDs and a validated revision, never arbitrary commands or mount flags. It uses an allowlisted environment, disables system/global configuration, hooks, filters, fsmonitor, external diff/pagers, automatic maintenance, credential helpers and network protocols. External gitdir/commondir/alternate paths and submodules are rejected unless a later explicit supported profile defines them. Source repository configuration is untrusted even when a read operation appears harmless. Every helper entry treats writable common metadata as untrusted: inspection and source import use an ephemeral Git metadata view containing only selected HEAD/index/refs/object references and a fixed clean configuration. Local/common/worktree configuration, includes and arbitrary filter drivers are never imported into that view. Managed common mutation uses a fixed clean configuration plus fixed command overrides. This intentionally supports a bounded managed Git profile rather than arbitrary repository Git customization. Git imports explicitly disable local clone hardlink optimization and alternate object stores; every imported object has an independent inode, so writable common metadata cannot mutate the read-only Local source through an alias. No host Git process reads project repositories. [Git configuration](https://git-scm.com/docs/git-config)

Non-Git copying is an explicit bounded snapshot operation into a new quota-backed checkout. Descriptor-relative traversal rejects special files, escaping links and path swaps, limits entries/bytes/depth, and preserves no cross-checkout hard links. Source identity and changes are checked before publishing. A conflict or quota exhaustion leaves an explicit failed creation record and only owned staging eligible for cleanup.

Every conversation binds to a stable workspace ID. Managed writers serialize per workspace; independent workspaces may run concurrently. Common Git metadata changes additionally serialize per project. Import and copy hold a source workspace snapshot reservation that conflicts with managed writers; before/after checks supplement that reservation for out-of-band changes. These reservations cover delivered Harbor clients, not arbitrary external SSH or repository scripts. Cancellation remains authoritative per session/turn. A terminal turn does not itself release its workspace writer reservation: Harbor first confirms owned runtime retirement, including background children. Unknown termination or uncertain work retains the reservation and is visible as blocked; another session cannot take it silently. Missing or replaced folders become unavailable with no path fallback. Removal first rechecks identities, dirty state, active reservations and runner/background-process state; Local workspaces are never deleted. Archive operations change metadata only and never imply source deletion.

An owner-browser-only release command may recover an uncertain workspace reservation. It requires explicit acknowledgement that prior effects are unknown and file changes remain, plus the expected reservation session and generation. The durable idempotent command rejects stale expectations and healthy active turns. The supervisor confirms exact owned runtime/background retirement and fences the old generation before releasing; unknown cleanup retains the reservation. Original uncertain sessions and operations remain uncertain and are never replayed. A different conversation may then acquire the workspace. P007 may invoke the same reservation compare-and-release helper after its own confirmed retirement without weakening these checks.

Workspace creation and removal first commit a durable storage command and stable workspace identity. The supervisor performs external effects only after that commit; trusted command-hash receipts outside project roots reconcile transport/COMMIT loss. Pending storage commands reserve project metadata and source workspaces across restart. Helpers are created without execution, then started using their immutable container ID rather than a reusable name; a delayed predecessor cannot start a successor. Creation staging may be discarded only after exact owned helper retirement; a completed receipt is replayed as a result, never as a second filesystem operation. Removal resumes only its recorded exact inode. Recovery history retains at most 64 terminal/pending records per workspace; failed retries of the same reservation reuse its durable record. Metadata storage commands retain at most 128 records per project and 4096 trusted receipts per installation (new creation stops at 2048 to reserve removal capacity). Their fixed-helper authorization is committed at acceptance; browser logout does not undo an already accepted metadata operation or grant later runtime execution.

## Persistence and verification

Migration 006 registers workspace type, lifecycle, canonical identity, common metadata identity, base revision, dirty-source policy and conversation binding. Native history remains session-stable and shares the project quota. Backup registration includes the workspace rows, all managed checkouts/common metadata and native history as one consistent project unit; P009 owns complete host restore evidence.

P003 verifies real UI/API/database/supervisor behavior with only external Codex/OIDC fixtures, malicious Git configuration and path swaps, independent writers, conflicting Local queues, dirty/active removal, and actual Linux disjoint mounts/quotas. Dedicated-account parallel native turns remain a mandatory separate live gate; missing credentials do not become successful skips.

Removal records its clean authorization and exact checkout/common identity in a durable `removing` receipt before the first unlink. Interrupted removal retains the project metadata reservation; after exact helper retirement it resumes only that recorded deletion without re-inspecting partially removed contents. Failed removals before this checkpoint may retry the same bounded operation and receipt identity; they do not append a new record for each retry. Private storage IPC rejects incomplete responses and enforces an absolute 45-second deadline independently of traffic.

Before publishing a completed receipt on the separate control filesystem, the trusted service retires the exact helper and completes a bounded `syncfs` barrier on the validated project filesystem. Successful effects awaiting this barrier retain an `applied` receipt and their result; flush failure or timeout stays pending and replay flushes without repeating the effect. Removal reconciliation and discarded staging use the same barrier. Process-death tests do not establish physical power-loss behavior; the Linux lane separately verifies the actual barrier and injected kernel-error publication ordering.

An `applied` receipt is not proof that pre-barrier project writes survived a host crash. Creation records bounded hashes of all checkout and common metadata contents plus their exact identities before publication; replay requires an exact match and otherwise remains pending without copying newer source data. Removal replay resumes its recorded exact deletion before flushing. The Linux fault scenario also corrupts an applied checkout and verifies that a successful flush alone cannot publish it.
