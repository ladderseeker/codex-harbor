## Problem and alternatives

A project preview serves arbitrary repository HTML/JavaScript. Hosting it under Harbor's own origin would give that code the browser authority of the trusted interface. Publishing a runner port would also create an access path outside Harbor's authorization gate. A general URL proxy would introduce a second network authority over host/control/private destinations.

Use a unique origin for each preview and a trusted connection limited to that preview's exact runner generation and loopback application port. The browser receives only a preview access grant, and project code receives no Harbor credential. P011 implements this boundary; P010's candidate inspection remains its own outcome and must meet the same origin/credential invariants without depending on the P011 UI.

## Browser origin and authentication

Configure one administrator-owned preview DNS suffix and its wildcard certificate. Each preview gets a random, never-reused hostname beneath that suffix, separate from Harbor's hostname and every other preview/candidate. The authority registry supplies the complete hostname; client input cannot select an arbitrary host, certificate or redirect. Production preflight checks the configured DNS/TLS profile and denies unknown hosts. Tests use their own wildcard test names and certificate through real Caddy, with no change to ordinary user DNS or trust stores.

The installed initial profile uses an optional fixed `previews` configuration containing `domain`, private loopback `port`, and administrator-owned wildcard `certificate`/`key` files. Caddy serves that suffix on HTTPS 443 and forwards only to the API's separate loopback preview listener; the supervisor owns the private relay socket. An absent profile disables preview admission. Preflight checks wildcard DNS resolution, certificate lifetime/hostname and key pairing; post-install acceptance must still demonstrate actual TLS and browser routing. The immutable release includes the fixed relay image even when this optional profile is disabled. Restored records are stopped history and receive a new random origin on an explicitly authorized new start.

Harbor cookies stay host-only with the existing `__Host-` prefix. A preview has its own high-entropy, hashed-at-rest `__Host-harbor-preview` cookie, Secure/HttpOnly and host-only, bound to preview ID, owner browser session, instance and runtime generation. It carries no API/PAT/launcher privilege. A new preview never inherits another origin's cookie, local storage or cache. Origin separation relies on actual scheme/host/port boundaries, not a different URL path. [Browser same-origin rules](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Same-origin_policy).

Opening begins with a CSRF-protected owner-browser command on Harbor that creates a bounded opening intent. A same-origin bootstrap document may consume that intent only under the same currently valid owner session; its URL contains only a noncredential operation ID. It posts a single-use, 30-second ticket in a form body to a fixed reserved endpoint on the exact preview origin. No reusable or one-time bearer appears in a URL, Referer, log or upstream request. The preview bootstrap validates the exact Harbor Origin, ticket/intent binding and current session/generation, atomically consumes the ticket, sets its own cookie, and loads a trusted nonce-protected landing page. Navigation from that landing page to the application starts within the preview origin. No arbitrary return URL or target window command is accepted.

The trusted Harbor bootstrap document alone uses `Referrer-Policy: origin`: a cross-origin form with `no-referrer` produces `Origin: null` in the tested Chromium browser and cannot satisfy the exact-Origin requirement. The origin policy sends only Harbor's public origin, with no opening ID, path, ticket or query. The landing page and all project responses retain `no-referrer`; this exception does not permit a missing or null Origin at the exchange endpoint. A bounded public-only browser probe established the header behavior during P011 implementation on 8 September 2026; full bootstrap acceptance remains part of P011-02.

Every proxied request and WebSocket upgrade rechecks the preview grant, source session expiry/revocation, current owner pin, preview state and generation before forwarding. Active/idle streams refresh authority at most one second apart and hold a nonrenewed authority lease of at most five seconds, additionally bounded by source/grant expiry. An independent deadline closes the transport when revalidation stalls/fails; no newly forwarded frame may pass an expired lease, even if a database query is still pending. Revocation or owner replacement must therefore deny further forwarding and close an idle connection within five seconds under the supported running profile, not only when traffic arrives. Cookies are never a substitute for Origin checks: requests with Origin require the exact preview Origin. Absent-Origin application requests require `Sec-Fetch-Site: same-origin`; the only additional application navigation case is a valid existing grant with `Sec-Fetch-Site: none`, `Sec-Fetch-Mode: navigate`, `Sec-Fetch-Dest: document` and `Sec-Fetch-User: ?1`, for deliberate direct/bookmark opening. Cross-site/same-site opening otherwise uses the fixed bootstrap, whose reserved endpoint has only its exact Harbor-Origin exception. Missing or unsupported Fetch Metadata is rejected, with a supported-browser explanation. Nonbrowser preview traffic has no implicit missing-Origin bypass; the initial profile is owner-browser content access only. PATs may manage permitted preview metadata/lifecycle under P011, but a PAT cannot mint a browser preview cookie.

Strip Harbor/preview access cookies and all Authorization, proxy-authentication and forwarding headers before traffic reaches project code. Bound ordinary application cookies and keep their names separate from the reserved `__Host-harbor-` namespace. Reject upstream cookies for that namespace or with Domain attributes; enforce Secure, host-only behavior. The trusted proxy owns security headers and ignores upstream attempts to replace them. Use `no-store`, `nosniff`, `Referrer-Policy: no-referrer`, COOP same-origin and a restrictive Permissions Policy. Deny framing, plugins, service/shared workers and access to Harbor's parent/opener context. The initial product opens a separate tab with noopener and has no embedding bridge.

Project scripts/styles may require inline code or evaluation; any such allowance exists only on the isolated preview origin. Its fixed CSP confines resources and connections to that origin plus specifically bounded data/blob media, denies external forms/frames/objects/workers, and applies a sandbox with only scripts, same-origin application behavior and same-origin forms. Stable Harbor's script/style policy is not loosened. Do not forward application redirects to another origin or the reserved bootstrap path; allow only validated same-preview redirects. Service-worker denial is essential so a previously loaded project cannot later intercept the trusted bootstrap or serve a new preview's private content. Revocation cannot erase content a browser has already received. [CSP sandbox behavior](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/sandbox).

These browser controls protect Harbor's credentials and origin and restrict the specifically tested resource/connection/navigation paths. They are not an operating-system firewall around the owner's browser or a universal data-exfiltration prevention claim. D001 and the no-network runner/relay profile own actual server-side network confinement. Project content remains untrusted even when opened by its owner.

## Runner and trusted relay

A preview owns a dedicated confined runner and a narrow relay, never an existing conversation or terminal process. The fixed initial execution profile uses the pinned Node/npm/Codex image to run one validated package-script name under a server-owned argv/environment template. Repository scripts are untrusted code executed only inside that runner. The supervisor uses the adapter's capability-tested `command/exec` lifecycle; it does not run project scripts itself. The preview runner has no model account, model gateway, external network, Docker socket, host credential or unrestricted launch flag.

The application binds its selected allowed port on the runner's loopback address. A separate fixed relay container joins only that exact runner's network namespace with `--network container:<validated immutable container ID>`. It has no project mount, credentials, host network, extra network attachment or published port. It retains its own PID/mount namespace, fixed nonroot UID, read-only image, dropped capabilities, no-new-privileges, seccomp and strict resource limits. Docker supports sharing a specific container's networking stack; this must be demonstrated on the supported Linux profile rather than inferred from a macOS test. [Docker container networking](https://docs.docker.com/engine/network/#container-networks).

The trusted broker controls the relay over private framed stdio/IPC and accepts only an opaque preview ID. Both broker and relay fix the upstream to literal `127.0.0.1` and the stored permitted application port. There is no DNS resolution, absolute URL, CONNECT, arbitrary TCP tunnel or client-selected container. The relay validates bounded HTTP method/path/header/body frames and only the explicitly implemented WebSocket framing. It forwards no control-plane credential to the runner. Upstream bytes cannot become a broker command or host path. Recheck exact runner/relay identities and authority after waits; a stopped/replaced runner invalidates the channel and all grants, without looking up a successor by a reused name.

Persist the launch intent and exact runner/relay identities before relying on a started process. If launch acknowledgement is lost, reconcile only those exact resources; do not start a second application automatically. Stop closes access first, then retires the dedicated relay and application runner and confirms absence, including background processes, before releasing its reservation. Unknown retirement stays blocked and visible. No preview action implicitly stops a conversation or terminal.

## Workspace reservations, data and consequences

The default preview mounts the selected checkout and any D005 `/git-common` mount and selected-workspace alias read-only. Apply the same registered project/Local/derived checkout and common-directory identity/ancestry validation at launch; the native read-only sandbox receives no additional writable project or Git-common root. Its fresh private native home and bounded temporary directory do not authorize writes to shared project metadata. It owns an explicit generation-bound reader lease that may coexist with ordinary file/turn writers; source changes can therefore become visible to an application that reloads them. Project/workspace metadata operations such as removal, copy snapshot, archive or Git-common restructuring must account for active reader leases and refuse incompatible changes. Read-only does not promise a filesystem snapshot. Applications requiring writes use an explicit workspace-write profile and the same exclusive typed writer reservation as other features, with only D005's validated selected-workspace/common roots below the administrator ceiling. Both profiles retain project quota, finite runtime and process limits; a read-only app must place transient cache/output in its bounded temporary directory or report its write failure.

The lease is a resource-lifetime record, not an authorization grant. Its owner, kind and epoch are exact; only confirmed retirement can release it, and P003/P007 recovery cannot clear another feature's owner. P011 extends the shared metadata/admission checks instead of adding a competing lock. Read-only terminal/conversation policies remain unchanged. Preview lifecycle, reader leases, grants, opening intents and bounded logs belong to its P009 module registry; the complete project unit continues to own its physical data. Restore leaves previews stopped, grants revoked, stale launches non-replayable and source-host identities historical.

This design adds a trusted relay protocol, wildcard preview DNS/TLS configuration, and a tested reader-lease integration. It deliberately supports a bounded initial Node package-script profile with dependencies already present, HTTP/1.1, SSE and explicitly tested WebSockets. Dependency installation, public links, arbitrary upstream services, external browser fetches, service workers, embedding, generic port forwarding and unsupported protocols remain outside the first profile. They require separately recorded capability/security work instead of silently bypassing the boundary.

## Review and delivery

Prepared against main `3116fcc` within the owner's authorized roadmap. One independent design review found missing explicit D005 read-only common-mount/sandbox restrictions, an unspecified maximum idle-stream revocation latency, and stale embedding wording in P011. The corrections explicitly preserve D005 identity/read-only roots, bound revalidation to one second and nonrenewed stream authority to five seconds, and limit initial opening to a separate tab. The reviewer rechecked those corrections and closed the bounded design review with no remaining actionable finding. Main additionally made absent-Origin navigation handling explicit and limited browser-confinement claims to the stated policies. The decision is Accepted; implementation began on 8 September 2026 and remains In progress. P011-01–06 own actual application, hostile-browser, separate-origin, HTTP/stream and Linux relay/mount/egress evidence. Record precise header/bootstrap/navigation behavior with real Chromium and TLS checks before claiming delivery. No proxy, reader lease, capability or deployment command exists merely because this decision describes it.
