## Deferred self-development contract

Everything in this section is a retained target requirement for a future selected implementation. It does not advertise an available broker, panel or command.

Register Harbor's source as an ordinary allowed project and select a separate development worktree. Through the running conversation, request a source change, invoke the same development/build/test entry points used locally, inspect candidate results, and prepare an immutable artifact for promotion. A candidate URL is available only through its authenticated private route. Failure can be inspected and cleaned up from stable Harbor or the external recovery path.

The initial self-development workflow does not require the file-editor UI, interactive terminal UI, general preview feature, scheduler, or extension manager. the conversation service’s agent execution performs source edits; this feature provides its scoped build/test authority and candidate inspection route. It does not allow a task to edit the running deployment directly.

## Broker and isolation contract

Implement a trusted build/test broker outside coding runners. It accepts only registered worktree/snapshot IDs, a server-owned command profile, and bounded resource requests. Snapshot source before execution and record its digest. Scripts and Dockerfiles remain untrusted input: the broker runs them in restricted build workers, not its privileged process.

The broker provisions the [D008 worker and disposable guest](../decisions/008-isolated-self-development-workers.md), using fixed mount/network/launcher templates. The guest contains actual candidate services, its own native Docker daemon, separate database/role, volumes, Codex home, identity configuration, URL/ports and credentials. The nonroot outer worker container is the host boundary even if the guest and QEMU process are compromised. Candidate supervisor launch authority reaches only disposable guest resources. Names alone are insufficient: enforce resource ownership at the broker/OS boundary and reject stable/other-candidate IDs.

Coding tasks receive no host Docker socket, daemon credentials, arbitrary mount flags, privileged nested Docker, or host-admin token. A short-lived capability may invoke only the assigned test job and inspect its output; it cannot administer deployments or mint broader credentials. Standard command wrappers route supported build/test profiles through this broker in a Harbor runner and use equivalent trusted local provisioning from a developer shell. Upon delivery, this path must work without manually bypassing isolation.

Reserve capacity for stable Harbor, enforce candidate quotas/lifetimes, and clean up by manifest. Candidate tests use synthetic state and external fixtures; real runtime/isolation evidence remains separately required. Promotion references the tested artifact digest/report and follows the managed deployment service’s independent release path and current user authorization. Deployment credentials never enter candidate code; replacing the supervisor drains or explicitly interrupts its active control session.

## User/API, authority and durable jobs

The conversation's Development panel lets the owner enable the fixed command profiles for its Harbor source workspace, see capability expiry, submit a build/check/test, follow bounded logs and phase changes, open an authorized candidate, stop it, and prepare the exact verified artifact for P009. Show source and artifact identities, changed-source conflicts, queued/capacity results, failed checks, expired grants and uncertain retirement. A prepared artifact is distinct from a promoted release; the panel must not label missing live/checkpoint gates as passed. Reconnecting a browser shows the existing job and its log replay floor without resubmitting it.

Add versioned browser routes for development capabilities, job list/detail, submit, cancel, confirmed-retirement acknowledgement, candidate open, artifact metadata/download and release preparation. Mutations use current owner/session/instance authority, exact Origin, CSRF, expected revision/generation and the existing timestamped idempotency/request-hash contract. Capability issuance and job submission require the assigned project and workspace-write ceiling. Stop/read do not require a target write ceiling. Browser-issued development grants are separate from P002 PATs; existing PATs gain no development administration or promotion routes implicitly. the token policy’s current-authority helpers and project ceilings remain shared implementation dependencies.

Runner requests go through D008's narrow gateway and assignment capability, not the browser API cookie. Use 32 random bytes, a purpose-separated stored hash, exact instance/owner/project/workspace/conversation generation, a fixed profile allowlist and expiry no later than two hours or its issuing authority's expiry. Issue at most one active capability per conversation and 16 per instance, at most eight accepted jobs per capability. Replacing one revokes future use of the old value. Never return the raw capability in ordinary APIs/events/logs; the trusted launcher publishes it only to that runner's read-only assignment file. Before any new dispatch, verify the current source authority, live generation and capability after lock waits. An already accepted bounded job may finish after browser logout; current browser authority is still required to inspect it or prepare a release.

The broker accepts only opaque registered source/job/profile IDs and bounded expected metadata. It commits capture intent and resource reservation before filesystem/container effects. Source conflicts produce a failed capture with no build; explicit retry uses a new capture of current bytes. A lost response returns the original job and immutable input. Worker launch/retirement uses a recorded immutable container ID and owned image/mount manifest, never a reusable name alone. A crash after launch but before acknowledgement becomes reconcilable `uncertain`, never an automatic second guest. Existing jobs survive API/browser restart, and broker restart first reconciles exact owned resources before new admission.

Persist jobs, capability hashes/revocation, phase/attempt state, source manifests/digests, artifact digests and compatibility, independent verification outcomes, candidate-view references, log watermarks, control intents and bounded audit outcomes. Preserve owner gate → actor/capability → project → workspace → conversation/job lock ordering. D008 owns the explicit optimistic capture from the requesting writer; ordinary conflicting writers and project metadata reservations still block capture. The copy's immutable manifest is authoritative even if the editable workspace changes later; the UI displays that distinction.

A successful build seals the exact artifact, retires its build worker, and starts a fresh verification worker from the sealed administrator guest base. Trusted fixed tests and report authority outside both guest and outer worker determine pass/fail and bind the report to those exact bytes. The separate confined candidate browser holds only disposable candidate credentials, not stable browser/admin authority. A candidate's own successful exit or forged worker report cannot bypass failed external checks or write the trusted report store. Verification results bind source/artifact, worker/base/policy/dependency digests, required check IDs, environment and timestamps. A later source edit does not mutate an existing result, and artifact substitution invalidates release preparation.

`pnpm dev` requests inspection of that candidate under a unique HTTPS hostname. Reuse D007's one-use browser bootstrap, host-only viewing cookie and current-authority stream checks with a fixed broker-to-guest target, rather than the preview service’s project launcher. P011 need not exist first; common grant/proxy primitives belong in shared modules. Candidate fixture OIDC and Harbor session cookies remain independent of stable cookies. Hostile candidate HTML cannot execute under the stable origin or receive a stable/broker credential. Do not expose guest SSH, QMP, Docker, database or generic forwarding through this route.

## Resource limits, cancellation and recovery

D008 owns the hard worker/host reservations. Application admission allows one executing worker and one queued job per instance; a ready inspection worker still occupies that capacity. Limit stored jobs to 32 per project/128 per instance, source snapshots to 256 MiB/30,000 entries/depth64/16 MiB per file, artifact files to 2 GiB and retained artifact bytes to 8 GiB per instance. The broker verifies an actual Harbor source layout and a pinned frozen lockfile; it does not build an arbitrary host path. Retain at most two unreferenced snapshots/artifacts per project; referenced active or uncertain resources cannot be garbage-collected. Refuse new work when evidence or quota limits prevent safe admission.

Each job has a two-hour total lifetime; bound its startup, command and transfer phases separately within that deadline. Logs retain at most 2 MiB per job for 24 hours, with bounded chunks, explicit truncation/replay floor and safe text rendering. Cap structured reports at 256 KiB; cap list pages at 50 with filter-bound five-minute cursors. Keep at most 32 accepted ordinary command aliases per capability. Reserve separate cancel and retirement-acknowledgement operations for each unresolved job, each reusing its own stable ID with at most three expected-attempt retries and three audit outcomes. Exact-key reconciliation precedes capacity checks; repeated controls do not append aliases or consume the other control's reserve. Unknown cleanup retains capacity and requires the documented exact administrator recovery path.

Cancellation first closes candidate viewing/dispatch, records stopping, retires the exact worker and background children, then marks stopped and cleans only its owned paths. Cancelling a candidate never cancels the stable coding conversation. Late callbacks from a retired worker cannot publish results or affect its successor. A failure during artifact extraction/publication leaves owned staging with no prepared release; recovery verifies exact manifest/digest and either finishes that publication or reports uncertainty, without executing a candidate hook on the host.

The managed deployment contract must back up durable job/source/artifact/report metadata and the retained release artifacts, with complete module coverage. Disposable guest disks, probe/test homes and candidate credentials are excluded. Restore revokes capabilities/viewer grants, retains historical outcomes and disables every old queued/running job; it never contacts source-host workers or restores their launch authority. Managed promotion must consume only the exact independently verified artifact with compatible schema/native/runtime checks and all required release gates. A checkpoint or migration failure leaves stable admission/state governed by the managed deployment contract, never by a candidate's claimed success.

## Deferred managed extension contract

Everything in this section is a retained target requirement for a future selected implementation. It does not advertise available extension configuration or execution.

The initial matrix contains two local profiles: a skill directory with `SKILL.md` and supporting files, and a self-contained Node.js STDIO MCP bundle with a relative `.mjs`, `.cjs`, or `.js` entrypoint. Dependencies must already be included in the bundle or pinned runner image. Harbor performs no package installation, setup script, marketplace access, remote HTTP connection, OAuth flow, credential injection, or host executable discovery for this feature. These exclusions select an explicitly tested local profile from the original local-or-remote scope. Unsupported configurations receive a visible unsupported result before execution; no desktop plugin or universal MCP compatibility is claimed.

The owner selects a registered source workspace and relative directory, inspects its immutable snapshot, and enables that version for the project. Conversations then use it with their own selected workspace and permissions. Source edits do not alter an enabled version: explicit refresh creates a new snapshot and configuration revision. Skills are selected in the composer; MCP tools have a conversation picker and explicit tool action, as well as model-directed use during an authorized turn. Effective configuration, tool startup/status, safe descriptions and errors remain visible.

An editor, terminal, preview or deployment UI is not required to configure extensions. Managed workspace admission provisions the source directory through approved project work or a fixture. Existing schedule-grant and managed backup integrations must satisfy the obligations below when the deferred extension outcome is implemented.

The project Extensions panel lists versions and offers Add skill, Add local MCP, Refresh source, Enable, and Disable. Show source workspace/path, digest, current project revision, enabled/effective state, profile, selected-workspace access, and whether running work would be interrupted. The initial credential reference is `none`; reject credential fields instead of silently ignoring them. Descriptions, filenames, schemas, errors and results are untrusted text: no HTML, remote icons, images, or automatic URL requests.

Add narrow versioned routes for project extension lists/details and durable create/refresh/enable/disable operations, conversation effective configuration/tool discovery, and conversation tool invocation/cancellation. Requests contain registered IDs, expected revisions, relative source paths, supported profile fields and bounded JSON arguments. They cannot carry app-server methods, native paths, commands, shell arguments, environment maps, mount roots, destinations or raw TOML. Extend OpenAPI and the existing operation/event envelope. The timestamped idempotency contract compares the complete normalized request hash.

Configuration and source publication are owner-browser-only, with current owner/session/instance checks, exact Origin and CSRF. P002 tokens gain no implicit configuration/probe access. Existing execute-scoped clients may select registered skills in an ordinary turn under their project/permission ceiling and the same revision checks; direct MCP actions initially remain owner-browser-only. Existing cancellation authority can stop a tool action without a write ceiling. Elicitation answers reuse the conversation service’s current approval authority and cannot expand the original permissions.

Source snapshotting is a fixed P003-style metadata operation: commit a stable extension/version ID and validated source identity, reserve the source against managed writers, then perform the bounded copy. This action grants no later execution by itself. Registration leaves a version disabled. Enabling or probing is explicit execution authorization for trusted project code; even requesting a tool list may have effects. Probes name their workspace and run read-only, account-free and network-disabled in a disposable runner. Never probe disabled code automatically on page/list access. Normal tool actions use the conversation's actual permission profile and writer admission, not an MCP annotation's claim of read-only behavior.

The composer selects at most four enabled skill IDs and records the current extension revision in the accepted turn. The server resolves their immutable `SKILL.md` paths into pinned `UserInput.skill` values. An explicit MCP action records server/version/tool identity and JSON arguments, serializes with ordinary conversation work, and displays a separate persisted tool activity. It makes no model request and is not fabricated as an assistant answer or a native history item. Model-directed MCP calls retain their real native item provenance.

## Immutable sources and trusted configuration

The storage service copies only the selected directory beneath the registered workspace, using descriptor-relative traversal and before/after source checks. Reject escaping/absolute paths, `.git` metadata, symlinks, hard-linked input files, special files, invalid UTF-8 paths and identity swaps. Copy into fresh inodes in a root-owned extension directory inside the project's hard quota but outside writable checkouts; preserve no ownership or executable/special mode bits. The manifest records paths, sizes, hashes, source workspace identity and final directory identity. Publication uses stable IDs, exact helper retirement, filesystem durability and command-hash receipts as in D005. A lost result reconciles its original effect instead of snapshotting newer source. Inspection never executes project code in the API, supervisor or storage service.

Limit a snapshot to 16 MiB, 1,024 files, 16 directory levels, 1,024 bytes per path and 4 MiB per file; `SKILL.md` is UTF-8 text of at most 64 KiB. Limit each project to 32 extension records, 16 enabled skills, four enabled MCP servers and 64 MiB of snapshots; instance limits are 256 records and 256 MiB. Admission checks these limits and D003's hard quota. Retain at most four unreferenced historical versions per extension; versions referenced by active/uncertain operations remain pinned and count toward the limit. Refuse further growth rather than deleting referenced evidence. Unused-version removal checks its exact registered identity and never removes source files.

Mount only the selected immutable versions from the conversation's project, read-only at fixed identity-derived paths. Revalidate trusted ancestors, root ownership, device/inode and manifest bytes before mount resolution under D002/D003. No other project's bundles, global owner skill directory, developer home or native credential store is imported. Enabled skill names are unique within the project and validated/bounded; unresolved declared dependencies produce unsupported status, never automatic installation.

For MCP, derive the native server name from its registered ID and use the fixed Node executable with the selected relative entrypoint. Its working directory is the conversation's `/workspace`. Reject caller-defined Node flags, preload/module search paths, inherited host environment, network endpoints and native addon profiles. Fix native startup/tool timeouts at 10/60 seconds. Generate configuration from enabled, hash-validated local profiles only, with unsupported plugin/app/hook/remote extension surfaces disabled. Repository configuration must not add MCP servers or override policy; inspect effective native configuration before dispatch and fail closed on mismatch.

Managed skill selection is explicit: disable the native automatic skill instruction catalog and bundled skill advertisement using pinned fields, and set process extra roots to the enabled immutable versions. Public discovery and input resolution expose only registered enabled IDs. The toggle controls Harbor's managed discovery/dispatch; it is not filesystem access control on the original project text. Authorized code or a model reading project files can still read instructions stored there. Do not claim disabling a skill makes that source unreadable or prevents similar approved project code from running.

MCP executes in the assigned runner with the conversation's existing UID, mount, capability, process, quota and network bounds. Read-only profiles have physically read-only checkout/common mounts; workspace-write profiles hold the existing exclusive writer reservation. Native tool annotations/approval cannot loosen those mounts. D001 permits only the fixed model transport for conversation runners; this feature adds no remote MCP/development egress. Trusted local MCP code may access credentials used by its own native conversation runtime, as qualified in the architecture/D004; it receives no additional service, control-plane, host or other-project secret. Account-free probes receive no model credential.

## Revision, dispatch, disable and recovery

Persist project configuration revisions, extension/version manifests and identities, enabled state, profile/source metadata, effective runtime revisions, durable commands and bounded results. Native configuration files are generated projections, not policy authority. A new/resumed runtime applies and verifies its recorded revision before dispatch. An idle runtime with a different revision is retired exactly, then relaunched against the same native history; do not silently change a loaded generation's policy. Browser or API restart does not relaunch dispatched work.

Every accepted turn, manual tool action and probe captures the extension revision. Recheck current actor and revision after shared lock waits and immediately before external dispatch. A changed revision makes undispatched work visibly stale and requires a new explicit request; it cannot silently gain new tools. Preserve owner gate → actor → project → workspace → conversation/operation lock ordering, with configuration rows under project authority. If P008 exists, its grants capture the extension revision; configuration changes pause affected schedules until preview and grant renewal. Already accepted fixed storage effects may reconcile without authorizing another execution step.

Enable/refresh applies to future generations; active work continues with its recorded revision, visibly distinguished from current settings. Disable first durably removes future admission and invalidates queued dependent work. For a live generation containing the extension, the action explicitly says **Disable and stop affected conversations**, records exact generations and shows the affected count. The supervisor blocks new Harbor dispatch immediately, expires pending elicitation answers, interrupts affected work, and retires exact runners including MCP/background children before reporting `disabled`. Until retirement is confirmed the state is `disabling` or `uncertain`; already running code may finish effects during that interval. An old receipt cannot retire a successor, and no action claims completed effects were undone.

Manual tool actions use the existing durable dispatch lifecycle: intent before native send, exact conversation/generation/operation association, writer ownership until confirmed retirement, and `uncertain` after ambiguous transport or result COMMIT loss. Never replay automatically. Reconciliation may inspect state without reinvoking the tool. Explicit acknowledgement after exact retirement permits new work while preserving original uncertainty/provenance; reuse shared conversation fencing, without requiring its UI for minimal extension recovery.

Support pinned `mcpServer/elicitation/request` standard `form` through the existing approval/input surface. Accept a bounded object schema with at most 16 primitive string/number/integer/boolean/enum fields and bounded labels/options/values; no remote references, nested executable schema, URI navigation or credential autofill. Validate the response against the supported schema and current actor/generation before the first answer. First answer wins across tabs. A direct call's nullable native turn ID must map to its exact pending tool operation. The displayed/recorded input deadline is the earlier of the conversation service’s five-minute policy cap and the parent tool's remaining 60-second call budget, with five seconds reserved for answer delivery. Do not assume native timeout pauses for input. Track a direct call from its dispatch; a model-call form needs an observed, unambiguous parent tool start and a supported timing contract. If the remaining budget cannot be established, decline the request explicitly. Native timeout/resolution, operation cancellation and generation retirement immediately expire the input, even before its displayed deadline. Unsupported URL/OpenAI-form variants, requests for Harbor/host secrets, excess permissions, stale requests and expiry are declined/cancelled, never auto-approved. Approval adds no filesystem/network authority.

Allow one tool action/probe at a time per conversation, one project probe, and four probes per instance, with a 90-second probe lifetime. Bound discovery to 64 tools/server, 8 KiB per description/schema and 256 KiB aggregate; over-limit catalogs cannot leave partial callable entries. Arguments are at most 32 KiB/depth 16; results at most 256 KiB, plain text/JSON with explicit omission markers and no embedded-resource fetch. Existing runtime line, mailbox, process and native-history bounds remain enforced; malformed/flooding code can trigger exact runner retirement with a visible failure. Retain 128 settled ordinary extension commands/project. Each unresolved extension/generation target separately reserves one disable operation, one cancellation operation and one retirement-acknowledgement operation; one action cannot consume another's slot. Reconcile an exact existing key before any admission/retention check. Additional keys for an existing control return its operation reference without accepting or storing another alias. A failed control retries its same operation with expected-attempt comparison, at most three recorded attempts and three audit outcomes per action; no repeated click creates a fresh record. Exhausted attempts remain visibly unresolved and require exact administrator recovery, never silent reservation release. Tool activity shares conversation history/operation ceilings. Lists use pages of at most 50 with filter-bound five-minute cursors. Operational audit logs contain no bundle bytes, tool arguments or returned secrets.
