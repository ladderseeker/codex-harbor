## Conversations

The [personal local profile](004-deployment-and-profiles.md) supports native account login under [D010](../decisions/010-personal-local-experience.md). It does not satisfy or waive the managed profile's dedicated live-account and Linux gates.

Use the [architecture's state/API contract](../architecture.md#api-events-and-state-transitions). Persist project/workspace, facade session/native thread mapping, operation intent, effective execution grant, approvals, and events. One active turn per conversation; additional input is explicitly queued or steered. Duplicate submissions resolve to the same operation. An ambiguous runtime delivery is never silently replayed.

Implement normal authorization on pages/assets, cookie API requests, and SSE. Use a disposable real OIDC provider for deterministic tests, not an auth bypass. Keep app-server private, protect the owner credential onboarding flow, enforce permission ceilings and project-root confinement, and isolate coding processes from Harbor configuration/database credentials. Render streamed content as untrusted. Render assistant replies as CommonMark with GFM tables, task lists, strikethrough and autolinks; preserve fenced code literally, including longer outer Markdown fences around inner code fences. Reparse accumulated text during streaming and after history reload without changing stored source. Raw HTML and unsafe URL schemes must not execute; remote images must not load automatically. Mermaid may use a clearly labeled source-code fallback. Keep user input and tool diagnostics literal. Use the canonical conversation typography and contained horizontal scrolling for wide tables/code. Baseline quota/retention settings, logout revocation, and emergency stop are part of the feature, not deferred security hardening.

[D004](../decisions/004-protected-runtime-credentials.md) defines the initial capability and encrypted credential onboarding path. Initial bounded conversation storage admits at most 2 MiB of text, 2,000 messages, 500 operations, and 100 approvals per conversation, with a 32 KiB approval scope. Stop admitting new work before reaching these limits; preserve cancellation and recovery. Event replay retains at most 2,000 events and seven days, with explicit snapshot resynchronization for older or missing cursors. These limits govern the initial implementation and must be visible to the owner. Durable history and unresolved work do not expire through replay cleanup.

Retain active and uncertain idempotency records throughout their operations and completed tombstones for the 24-hour retry window. Reject old immutable timestamps after collection, rather than treating them as new intent. Apply ordered, checksum-validated SQL migrations under an exclusive migration lock; a changed previously applied migration fails explicitly.

Browser closure and API restarts leave the supervisor's subscriptions and work alive. A runtime crash produces a safe interrupted/uncertain state with preserved native history; history navigation and explicit recovery follow the contract below. Pending approval survives a viewer disconnect, expires with its runtime generation, and is answered once after current authorization is rechecked.

Only the owner signs in. OIDC pins issuer and subject with PKCE/state/nonce and exact callbacks; secure opaque server sessions protect assets, APIs and streams. Keep current authority checks after blocking locks and before each new dispatch. Logout removes interactive access without undoing an accepted execution grant. Emergency stop separately blocks new work and retires owned execution. The supervisor survives browser/API disconnect, and native runtime loss becomes interrupted or uncertain. Use the architecture’s durable intent, epoch, replay and idempotency contracts.

## Programmatic access

Owner settings support token creation, scope/project selection, expiry, last-use metadata, and revocation. Display the raw token once. A script authenticates with `Authorization: Bearer`, discovers the versioned API, submits work with an idempotency key, follows events, reads the result, and cancels permitted work. Authentication errors return API errors rather than an HTML login redirect.

Publish OpenAPI and streaming-event schemas for delivered capabilities. Cookie-authenticated UI and machine-token access share the supported external contract. Extend explicit route policies only when the corresponding capability is delivered. Public registration, multi-user roles, raw Codex RPC forwarding, and unlimited administration tokens are excluded.

Store token identifier/prefix, verifier hash, owner binding, explicit capabilities, allowed project IDs, expiry, revocation, and audit metadata. Never persist or log raw tokens. The authority of a request is the intersection of token grants, resource ownership, and current server policy. Execution/approval scopes include a maximum execution profile; a token cannot gain a stronger profile indirectly through a prompt, configuration change, or approval answer.

Use the [shared operation/idempotency rules](../architecture.md#api-events-and-state-transitions). A revoked token cannot start queued work or retain a stream. Already-running work follows its recorded execution grant; revocation is distinct from emergency stop. Token management itself requires owner-browser authority with appropriate CSRF/session checks. No token is accepted from query strings or browser local storage.

P002 uses four explicit scopes: `read`, `execute`, `approve`, and `cancel`, with project UUID grants and a read-only or workspace-write ceiling. Tokens expire in 1–90 days. Token management remains browser-only. Up to 100 token records are retained per instance; revocation records remain durable. Creation retries return metadata with `secretUnavailable: true`; the raw secret is returned only on the first successful response and never enters the idempotency record. A lost first response requires revoke/recreate. Unknown routes remain browser-only until an explicit scope/resource policy is added.

## History and recovery

### History and metadata

Conversation archival changes visibility only and preserves the existing `archived_at` field. Project/workspace archival still requires idle admission. The legacy conversation archive endpoint uses the same visibility-only metadata semantics.

`GET /api/v1/history` uses a bounded query (at most 120 characters), active/archived/all filter, optional project ID, a stable `(created_at,id)` keyset cursor, and page size 1–50. Search matches title and durable message text with a bounded plain-text snippet; results never render HTML. Pagination order is immutable creation order so a rename or new event cannot silently move an existing result across pages. A search cursor includes its query/filter fingerprint and rejects use with changed filters. SQL statement timeouts and the existing conversation/message limits bound searches; pagination never counts all matches.

`POST /sessions/:id/metadata` carries `expectedRevision`, optional title and archived flag. Revision conflicts return 409. Archiving changes visibility only: source folders, native history, messages, queued/running work and approvals remain intact. Default navigation lists active sessions. An archived session remains directly readable and can be explicitly reopened/unarchived. Permanent deletion is excluded.

### Recovery state and explicit new input

`GET /sessions/:id/recovery` reports unresolved operations, current generation, last confirmed application cursor/state, and the latest recovery's bounded native-history/read status. Original uncertain operations remain `uncertain` permanently; a separate acknowledgement marker records the owner's later decision without relabeling old effects as successful.

`POST /sessions/:id/recovery` accepts an idempotency key plus `expectedGeneration` and requests confirmed fencing. Only a session with unresolved uncertainty is eligible. A separate durable recovery record moves `queued` → `fencing` → `ready`, or `failed`. Only one nonterminal recovery per session is allowed. Duplicate keys return the same record; stale generation or a competing recovery returns 409. Expired owner authority rejects an unstarted recovery. No ordinary turn is admitted during unresolved uncertainty or fencing.

The supervisor removes the exact captured runtime, waits for trusted confirmed absence, and reconciles the persisted launcher identity after process restart. It advances the session generation only after the old runtime is confirmed stopped. A bounded read-only runtime probe may inspect the saved native thread; it never sends a turn or approval and is itself retired with confirmed absence before `ready`. Known native assistant items can repair missing or nonfinal application projection items by stable native item ID. A confirmed complete application item is never overwritten by a conflicting or incomplete native read: the bounded report records conflict/truncation/gap provenance. Native reads are bounded to 2 MiB/2,000 text items; unavailable or truncated reads are explicitly reported and never imply complete history. Native read failure remains explicit and does not manufacture a complete transcript. Missing mapping or delivery evidence never changes the original uncertain operation into a success. All old pending approvals expire, and old queued turns are cancelled rather than silently released. Any unconfirmed retirement leaves recovery failed and the original uncertainty blocking.

`POST /sessions/:id/recovery/continue` requires `recoveryId`, its fenced `expectedGeneration`, `acknowledgeUnknownEffects: true`, and explicit new turn input/settings. In one transaction it verifies the ready fence, acknowledges the listed original uncertain operations, consumes that recovery, and admits a fresh operation through normal quota/policy checks. Exact retries return that same new operation. A new key after consumption, stale epoch, or competing caller returns 409. The original prompt is never automatically copied or resent. A failed transaction acknowledges nothing. Durable idempotency lookup precedes current generation/consumed-state preconditions so a response-lost accepted continuation still returns its original new operation after restart. Native approval requests remain pending when an answer is provably rejected before send; only transport/commit uncertainty poisons delivery. The owner may leave a ready recovery stopped indefinitely.

Recovery is owner-browser-only. Programmatic exposure requires an explicit policy descriptor rather than route-prefix inheritance. The supervisor releases only the exact workspace reservation after confirmed fencing and preserves original uncertainty; release alone never reconciles conversation effects.

### Replay and reserved control capacity

Replay rows are disposable projections; durable messages, operations, approvals, and necessary intent results remain intact. Each event transaction removes rows at or below `current_sequence - 2000`, and rows older than seven days, including unresolved sessions. A monotonic replay watermark records what was removed. Maintenance and snapshot/stream reads enforce the same age predicate; an expired cursor or any known internal gap returns explicit `resync`. Snapshot and its cursor are read under the same session lock; clients subscribe strictly after that cursor and replace their stream after resync.

Ordinary turn admission stops at 400 retained operation/recovery records in a conversation, with a hard 500-record total for new conversations. Migration preserves legacy histories that already consumed those slots: it stores a one-time ceiling of `max(500, existing operation count + unallocated active-turn cancellation slots + one recovery slot)`. This ceiling cannot grow through the API; legacy conversations at or above 400 cannot admit ordinary new work. This bounded migration exception preserves existing history and retroactively provides the missing stop/fencing reserve without deleting records. Admission also reserves one cancellation record for every outstanding turn lacking a control record and one session recovery record; it must prove `retained records + outstanding unallocated control slots + new turn/control pair + recovery slot <= 500` under the session lock before acceptance. A cancellation uses that target's reserved slot, coalesces pending/successful controls, and reuses a failed control's identity for at most three explicit attempts instead of appending records. A failed recovery is retried with `POST /sessions/:id/recovery` carrying `{recoveryId, expectedGeneration, expectedAttempt}` and a new key for the deliberate attempt. The transaction requires `state=failed`, the matching current generation and attempt, then increments the attempt and queues the same recovery ID. Exact old-key retries return their original accepted attempt without spending another attempt; concurrent distinct keys conflict. After three attempts it remains blocked with operator recovery guidance, not an indefinitely enabled retry action. A competing distinct intent never creates another active recovery. No-op controls against terminal targets reject without storing an intent. Original uncertain records and recovery acknowledgement history remain intact.

Ordinary browser mutation intents, including metadata changes, are serialized per owner and limited to 10,000 retained records. Guaranteed controls do not draw from a shared reserve that unrelated metadata can spend: each admitted turn reserves up to three bounded cancellation intent aliases; each persisted approval reserves up to three answer aliases; each recovery attempt uses one of its three request aliases and a ready recovery reserves one continuation alias. Control targets are validated existing UUID/epoch identities under the same session transaction. Duplicate/no-op new-key aliases cannot exceed that target's allowance; exact retained-key retries always reconcile first. Approval exhaustion fails closed, retains the pending request until deadline denial, and leaves the turn's separate cancellation/recovery path available. Recovery/cancellation retries reuse their target's operation/recovery identity, preserving their slots. A new operation after recovery may still receive an ordinary-work quota rejection; guaranteed fencing is not a promise of unlimited new work.

Control intent results are at most 8 KiB. Each recovery stores at most a 16 KiB provenance/report summary plus its bounded operation-ID list; native text repairs share the existing 2 MiB conversation-message quota. Recovery audit allowance is at most four rows of fixed action/correlation fields (under 512 bytes each): one per each of three deliberate fencing attempts and one consumed-continuation record, keyed uniquely so response retries/no-ops cannot append audits. Replay events are independently capped as above. These per-target allowances are reserved with the owning turn/approval/recovery, never charged to an unrelated actor-wide control bucket. Globally idempotent emergency stop uses its singleton durable state and does not allocate a new intent/audit alias each time it is already stopped; it remains available at logical history quotas. Physical database outage still denies mutations. Changed bounds require actual API/DB boundary verification.

If the optional P003 reservation-release hook fails or rejects its exact ownership CAS, reservation remains intact and recovery cannot become ready. Confirmed runner retirement alone does not authorize another workspace owner.

### Authority and settlement corrections

Fencing failures retain a bounded settlement repair until the database confirms `failed`; a failed terminal write cannot strand `fencing` indefinitely or release unresolved work. The supervisor stops admitting new work while its settlement repair is unavailable. Authority is locked before project/workspace/session locks and freshly evaluated after waits. Exact retirement, native inspection, and optional P003 reservation release stay serialized under that ownership transaction, preventing a competing recovery surface from retiring a successor.

Ordinary intent admission precedes callbacks that may allocate storage. Credential set/replace shares the 10,000 ordinary-owner intent budget. Self-revocation has one reserved intent per browser grant, so ordinary quota cannot prevent sign-out. Removing the currently configured encrypted credential version has one reserved intent alias and one audit; already-absent repeated removal stores neither. Credential set/removal audit writes are therefore bounded by admitted versions and the existing 30-day audit retention (at most two audits per admitted version; older legacy rows remain subject to retention). Existing-key reconciliation still happens before new admission, with fresh current authority before disclosure. External project registration checks authority after its admission locks immediately before filesystem effects; its accepted metadata grant survives expiry during those effects. The workspace service supplies durable storage intents.

History cursors preserve PostgreSQL timestamp microseconds as exact strings. A previously consumed recovery is retained as history but does not hide the fencing action for newly uncertain operations. Changes require the relevant history/recovery regressions.

The integrated recovery path locks the current actor, project, workspace and conversation in that order. It captures the workspace's actual `writer_generation`, independently of the conversation generation changed by supervisor restart, and holds those locks through exact retirement and reservation release. A missing reservation can be reconciled only while it remains unowned; another conversation's reservation blocks recovery. A derived-workspace probe uses the registered checkout and Git common-store identities. Normal confirmed completion releases its reservation while retaining acknowledged historical uncertain operations; unacknowledged uncertainty remains blocking. The legacy conversation archive route uses visibility-only semantics, while project/workspace archive retains its idle requirement. Token routing, project filtering, quota ceilings and fresh authority checks remain in force; Conversation recovery and metadata controls remain browser-only until explicitly scoped by a later design.
